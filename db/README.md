# db/ — schema อ้างอิงและชุดทดสอบ logic

ไฟล์ในโฟลเดอร์นี้เป็น **PostgreSQL อ้างอิงที่รันได้จริงและทดสอบผ่านแล้ว** ใช้พิสูจน์ว่า
เครื่องปันส่วนต้นทุนกับการคำนวณจุดคุ้มทุนทำงานถูกต้อง ก่อนจะไปเขียนเป็น Prisma ใน Sprint 2

โครงสร้างตรงกับ **ER v2** ใน [`../SA.md`](../SA.md) หัวข้อ 5 · เหตุผลการออกแบบอยู่ใน [`../COMPARISON.md`](../COMPARISON.md)

| ไฟล์               | เนื้อหา                                                                                    |
| ------------------ | ------------------------------------------------------------------------------------------ |
| `01_schema.sql`    | 34 ตาราง 1 view 6 ชั้น + constraint + `EXCLUDE USING gist` + catalog ค่าตั้งระบบ 10 รายการ |
| `02_functions.sql` | `run_cost_allocation()` · `compute_break_even()` · `calc_qstar()` · `get_setting()`        |
| `03_test.sql`      | seed + ชุดทดสอบข้อบกพร่องทั้ง 9 จุด + สูตร 1, 5a/5b, 6a/6b, 7 + แผนการรับนิสิตรายประเภท    |

## วิธีรัน

```bash
pnpm db:up
docker exec -i beps-postgres psql -U beps -d beps -q -f - < db/01_schema.sql
docker exec -i beps-postgres psql -U beps -d beps -q -f - < db/02_functions.sql
docker exec -i beps-postgres psql -U beps -d beps -v ON_ERROR_STOP=1 -q -f - < db/03_test.sql
```

`01_schema.sql` เริ่มด้วย `DROP SCHEMA IF EXISTS beps CASCADE` จึงรันซ้ำได้เสมอ (ข้อมูลทดสอบจะหายหมด)

## ค่าตั้งระบบ (`system_setting_def` / `system_setting`)

นโยบายการคำนวณที่เคยฝังอยู่ในโค้ด prototype ถูกยกขึ้นมาเป็น master ที่ **มีเวอร์ชันรายปีและต้องอนุมัติ**
กองแผนงานเปลี่ยนได้เองผ่านหน้าจอ W15 โดยไม่ต้องแก้โค้ด และตัวเลขปีเก่าไม่เปลี่ยนตาม

| key                          | กลุ่ม        | ค่าที่ยอมรับ                             | default              | ฐานปี      |
| ---------------------------- | ------------ | ---------------------------------------- | -------------------- | ---------- |
| `qstar_primary_method`       | calculation  | `sum_of_programs` · `pooled`             | `sum_of_programs`    | ปีการศึกษา |
| `cm_le_zero_policy`          | calculation  | `full_cost_recovery` · `not_computable`  | `full_cost_recovery` | ปีการศึกษา |
| `qstar_rounding`             | calculation  | `ceil` · `round`                         | `ceil`               | ปีการศึกษา |
| `profit_pct_basis`           | calculation  | `TC` · `TR`                              | `TC`                 | ปีการศึกษา |
| `default_revenue_mode`       | calculation  | `with_government` · `without_government` | `with_government`    | ปีการศึกษา |
| `default_allocation_method`  | allocation   | 4 วิธีใน `alloc_method`                  | `STUDENT_HEADCOUNT`  | ปีงบประมาณ |
| `depreciation_behavior`      | allocation   | `FIXED` · `VARIABLE`                     | `FIXED`              | ปีงบประมาณ |
| `reconciliation_tolerance`   | allocation   | ตัวเลข (บาท)                             | `0.00`               | ปีงบประมาณ |
| `outlier_min_q`              | presentation | จำนวนเต็ม (คน)                           | `30`                 | ปีการศึกษา |
| `non_academic_unit_in_total` | presentation | `true` · `false`                         | `true`               | ปีการศึกษา |

การอ่านค่าใช้ `get_setting(key, period_id, org_unit_id)` — ลำดับ: ค่าเจาะจงหน่วยงาน → ค่าระดับมหาวิทยาลัย → `default_value`
`affects_numbers = true` หมายถึงเปลี่ยนแล้วต้องสั่งคำนวณใหม่ (สร้าง `allocation_run` ใหม่) ผลเดิมยังอยู่ครบ

## การวิเคราะห์สัดส่วนจำนวนนิสิตเพื่อหาจุดคุ้มทุน (`scenario_admission_plan`)

ความต้องการจากที่ประชุม: ได้จุดคุ้มทุน**รวม**ของหลักสูตรแล้วต้องแตกต่อตาม**แผนการรับนิสิต** —
นิสิตไทย (ปกติ/พิเศษ) · นิสิตต่างชาติ (ปกติ/พิเศษ) · หลักสูตรต่อเนื่อง
ใช้ได้ทั้งตอนปรับปรุงหลักสูตรปัจจุบันและตอนเสนอเปิดหลักสูตรใหม่

| ตาราง                             | หน้าที่                                                                   |
| --------------------------------- | ------------------------------------------------------------------------- |
| `scenario_admission_plan`         | แผนการรับรายประเภท — หนึ่งแถวต่อหนึ่งช่องกรอกในตารางแผนการรับของ W7       |
| `scenario_result_by_type`         | ผลลัพธ์รายประเภท — สัดส่วน · รายได้ · TFC ที่ปันมา · TVC · ส่วนเกิน · Q\* |
| `scenario_admission_total` (view) | ผลรวมจำนวนนิสิตตามแผน ใช้ตรวจว่าตรงกับ `scenario_plan.q_input`            |

**แผนการรับกรอกได้ 2 แบบ** — `headcount` (รู้จำนวนคงค้างอยู่แล้ว) หรือ `intake` (รู้แค่รับปีละกี่คน)
คอลัมน์ `resolved_headcount` เป็น generated column ที่บังคับสูตร `รับต่อปี × จำนวนปี` ไว้ในฐานข้อมูล
จึงไม่มีทางที่ฝั่งแอปกับฝั่ง DB ตีความแผนการรับต่างกัน · **หลักสูตรต่อเนื่องใช้ `duration_years = 2`
ไม่ต้องมีประเภทนิสิตพิเศษเพิ่ม** เพราะสิ่งที่ต่างคือจำนวนปี ไม่ใช่ตัวนิสิต

⚠ **`q_star` รายประเภทขึ้นกับส่วนผสมที่กรอกเข้ามา** — TFC เป็นก้อนเดียวของทั้งหลักสูตร
ต้องปันตามสัดส่วนหัวนิสิตก่อนจึงพูดถึงจุดคุ้มทุนรายประเภทได้ เปลี่ยนส่วนผสมแล้วค่านี้เปลี่ยน
ถ้าคำถามคือ "ตรึงไทยไว้เท่าเดิม ต้องรับต่างชาติกี่คนจึงคุ้ม" ให้ใช้ `solveAdmissionTarget()`
ในเครื่องคำนวณ ซึ่งเป็น goal-seek และให้คำตอบที่ไม่ขึ้นกับการปันส่วน

## ข้อบกพร่อง 9 จุดที่แก้จาก `MANUS/*.sql` และ prototype

| #   | ปัญหาเดิม                                               | ผลถ้าไม่แก้                                                                                 |
| --- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 1   | `CHECK (fixed_ratio + variable_ratio = 1)` บังคับทุกแถว | แทรกกติกา `UNCLASSIFIED` ไม่ได้เลย                                                          |
| 2   | `fixed_ratio`/`variable_ratio` ไม่เคยถูกใช้ในโปรซีเยอร์ | รายการ MIXED 50/50 ไม่ถูกแยกจริง                                                            |
| 3   | ปัดเศษทีละแถว + tolerance 0.01                          | run ล้มเหลวแทบทุกครั้งเมื่อกระจายหลายหลักสูตร                                               |
| 4   | INNER JOIN กับตาราง driver                              | ต้นทุนที่ไม่มี driver หายเงียบจากยอดรวม                                                     |
| 5   | unique index กันแค่ `valid_from` ซ้ำ                    | กติกาที่ช่วงเวลาคาบเกี่ยวกันแทรกได้ทั้งคู่                                                  |
| 6   | `CHECK (amount >= 0)`                                   | รับรายการคืนเงิน/ปรับปรุงติดลบไม่ได้                                                        |
| 7   | `RAISE EXCEPTION` ตอน reconciliation ไม่ผ่าน            | rollback การบันทึกสถานะ `FAILED` ไปด้วย → ไม่เหลือหลักฐาน                                   |

| 9   | นโยบายการคำนวณฝังในโค้ด                                 | กองแผนงานเปลี่ยนเองไม่ได้ · ไม่รู้ว่าตัวเลขปีไหนใช้นโยบายใด · หน้าจอคนละหน้าใช้กติกาต่างกัน |

## ยังไม่ได้ทำ

- **RLS ตามคณะ** และการจำกัดสิทธิ์ระดับฐานข้อมูล
- **hash chain ของ `audit_event`** และ trigger บันทึกอัตโนมัติทุกตาราง
- **การปันส่วนหลายขั้น** (หน่วยสนับสนุนให้บริการกันเอง) — ปัจจุบันเป็นขั้นเดียว
- **`scenario_result` / `scenario_result_by_type`** ยังไม่มีโปรซีเยอร์คำนวณฝั่ง SQL — ตั้งใจให้
  ชั้นแอปคำนวณด้วย `@beps/calc-engine` (`calcAdmissionMix`, `solveAdmissionTarget`) แล้วเขียนผลลง
  เพราะการจำลองเป็นงานโต้ตอบสด ไม่ใช่ batch เหมือน `compute_break_even()` · ชุดทดสอบใน
  `03_test.sql` ตรวจสูตรเดียวกันด้วย SQL ตรงๆ เพื่อยืนยันว่าสองฝั่งให้ตัวเลขเท่ากัน
- **`qstar_primary_method`, `outlier_min_q`, `non_academic_unit_in_total`** มีในตารางค่าตั้งแล้ว
  แต่ยังใช้ที่ชั้นรายงาน/หน้าจอเท่านั้น (`compute_break_even` เก็บผลทั้ง 2 วิธีเสมออยู่แล้ว)
- **trigger บันทึก `audit_event` อัตโนมัติ** เมื่อค่าตั้งระบบหรือกติกาถูกแก้ — ตอนนี้ต้องให้ชั้น
  แอปเขียนเอง ทั้งที่เป็นตารางที่แก้แล้วกระทบตัวเลขทั้งระบบ
