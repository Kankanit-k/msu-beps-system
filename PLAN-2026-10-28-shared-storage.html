แผนงาน: ย้ายการตั้งค่าและผลคำนวณจากเบราว์เซอร์ไปฐานข้อมูลกลาง

MSU-BEPS · จากคำถาม “ผู้ใช้ระดับเดียวกันคนละบัญชีเห็นการตั้งค่าของกันไหม” · 28 ต.ค. 2569 · พักไว้ — ตอนนี้ระบบยังเป็น mockup ใช้ localStorage ต่อ (28 ต.ค.)

1สรุป

ตอนนี้การตั้งค่าและผลคำนวณทั้งหมดเก็บใน localStorage ของเบราว์เซอร์ จึงผูกกับเครื่อง ไม่ได้ผูกกับบัญชี

  • คนละเครื่อง หรือคนละเบราว์เซอร์ จะมองไม่เห็นของกันและกัน แม้อยู่คณะเดียวกันและบทบาทเดียวกัน
  • เครื่องเดียวกันที่สลับ login จะเห็นทั้งหมดเพราะไม่ได้กรองตามผู้ใช้ เช่น เห็นผลที่คุณเอื้องยืนยันไว้
  • ล้างข้อมูลเบราว์เซอร์แล้วข้อมูลหาย รวมถึงการล็อกคณะและผลที่ยืนยันแล้ว

เป้าหมายคือย้ายข้อมูลที่ต้องใช้ร่วมกันขึ้นฐานข้อมูลกลาง แล้วให้เซิร์ฟเวอร์เป็นผู้กรองตามบทบาทและคณะ โดยคงชื่อฟังก์ชันใน store เดิมไว้ หน้าจอจึงแทบไม่ต้องแก้

เงื่อนไขก่อนเริ่ม: production ยังตั้ง AUTH_DISABLED=true และบทบาท/คณะยังเลือกเองได้จากเมนูโปรไฟล์ ถ้าเซิร์ฟเวอร์ไม่รู้ว่าใครเป็นใคร ก็บังคับสิทธิ์การมองเห็นไม่ได้ ต้องเปิด login (อย่างน้อยเป็น mock login ที่บทบาทมาจาก configs/mockUsers.ts ฝั่งเซิร์ฟเวอร์) ก่อน (D5)

4โครงสร้างที่เสนอ

  1. ฐานข้อมูล: PostgreSQL ตัวเดียวกับที่วางไว้ใน docker-compose.yml (ที่ตั้งเครื่องดู D2)
  2. API: route handler ใน apps/web/src/app/api/store/… แบบเดียวกับ api/fixed-cost/simulate ทุก request อ่านผู้ใช้ บทบาท และคณะจาก session ฝั่งเซิร์ฟเวอร์ แล้วกรองตามตารางข้อ 3 ไม่เชื่อค่าที่ส่งมาจากเบราว์เซอร์
  3. ตาราง (ระยะแรก): เก็บก้อน JSON ตามรูปแบบเดิมของแต่ละ store ในตารางเดียว (D1) 
    app_record(id, kind, scope_year, scope_faculty, scope_program,
           owner_email, status, data jsonb, version, updated_by, updated_at)
app_record_log(record_id, action, by, at, memo, data_before jsonb)
    kind เช่น faculty-lock, faculty-class, program-result, account-rule, per-head-rate, admission-plan, sandbox-plan
  4. ฝั่งหน้าจอ: แก้เฉพาะข้างในไฟล์ store ให้เรียก API แทน localStorage และคงชื่อฟังก์ชันเดิมไว้ ระหว่างโหลดแสดง skeleton ถ้าบันทึกไม่สำเร็จให้แจ้งสาเหตุผ่าน toast
  5. ชนกันเมื่อสองคนแก้พร้อมกัน: ส่ง version ไปด้วยทุกครั้ง ถ้าข้อมูลถูกแก้ไปก่อนแล้ว ให้ตอบ 409 และแสดงข้อความ “มีผู้อื่นแก้ไขเมื่อ … โดย … กรุณาโหลดใหม่” (D6)
เมื่อทำ Sprint 2 (Prisma schema 32 ตารางตาม SA.md) ค่อยย้ายจาก app_record ไปตารางจริง (fixed_cost_policy, account_behavior_rule, per_student_charge, scenario_plan) โดยหน้าจอไม่ต้องแก้ เพราะคุยผ่าน store เดิม

5ต้องตัดสินใจ

D1 · รูปแบบตาราง ก) ตาราง JSON ตารางเดียว (ทำได้ภายในไม่กี่วัน ตรงกับรูปแบบข้อมูลที่หน้าจอใช้อยู่) · ข) สร้างตารางจริงตาม db/01_schema.sql เลย (ถูกต้องระยะยาว แต่ต้องแปลงรูปข้อมูลเยอะ และตารางต้นทาง เช่น program_version ยังไม่มีข้อมูล)
เสนอ: ก) ตอนนี้ แล้วย้ายไป ข) ใน Sprint 2
D2 · ฐานข้อมูลตั้งที่ไหน ก) Postgres บนคลาวด์ที่ต่อกับ Vercel ได้ทันที (เช่น Neon ผ่าน Vercel Marketplace) · ข) เซิร์ฟเวอร์ของมหาวิทยาลัย (ข้อมูลอยู่ในมหาวิทยาลัย แต่ Vercel ต้องเข้าถึงจากภายนอกได้ หรือต้องย้ายแอปไปรันในมหาวิทยาลัยด้วย)
เสนอ: ก) สำหรับช่วงทดลองใช้ แล้วถามศูนย์คอมพิวเตอร์เรื่องย้ายไป ข) ก่อนใช้งานจริง · ข้อนี้ต้องให้กองแผน/ศูนย์คอมฯ ตัดสินเรื่องที่เก็บข้อมูลการเงิน
D3 · สิทธิ์การมองเห็น ตามตารางข้อ 3 — ยืนยันแล้วเห็นทั้งคณะ · ร่างเห็นเฉพาะเจ้าของ · กองแผนเห็นทุกคณะ
เสนอ: ใช้ตามตาราง · ถามเพิ่ม: อาจารย์ประจำหลักสูตรควรเห็นผลที่ยืนยันแล้วของหลักสูตรอื่นในคณะไหม (เสนอว่าไม่เห็น)
D4 · ข้อมูลที่ค้างในเบราว์เซอร์ตอนนี้ ก) ทิ้ง เริ่มใหม่บนฐานข้อมูล · ข) มีปุ่ม “นำข้อมูลจากเครื่องนี้ขึ้นระบบ” ครั้งเดียว
เสนอ: ก) เพราะยังเป็นข้อมูลทดลอง แต่ประกาศให้ผู้ทดสอบรู้ก่อน deploy · ถ้ามีผลที่ยืนยันไว้จริงแล้ว (เช่น ของคุณเอื้อง) ให้กองแผนกรอกซ้ำ หรือเลือก ข)
D5 · เปิด login บน production ต้องรู้ตัวผู้ใช้ฝั่งเซิร์ฟเวอร์ก่อน ก) mock login (บัญชีใน mockUsers.ts) · ข) ERP login จริง พร้อมข้อมูลคณะ/หลักสูตรจาก ERP
เสนอ: ก) ไปก่อน และปิดตัวสลับบทบาท (SHOW_ROLE_SWITCHER ปิดอยู่แล้ว) ให้บทบาทมาจาก session เท่านั้น
D6 · สองคนแก้การตั้งค่าคณะพร้อมกัน ก) คนบันทึกหลังทับคนแรก · ข) ตรวจ version แล้วแจ้งให้โหลดใหม่
เสนอ: ข) กันการตั้งค่าคณะถูกทับโดยไม่รู้ตัว

6ลำดับงาน

รหัสงานขนาด
DB-0ตั้ง Postgres (D2) + ตาราง app_record / app_record_log + ตัวแปร DATABASE_URL บน Vercelเล็ก
DB-1เปิด login บน prod (D5) + helper ฝั่งเซิร์ฟเวอร์ที่คืน {email, role, faculty, program} จาก sessionเล็ก–กลาง
DB-2API /api/store/[kind] GET/PUT/DELETE + กรองสิทธิ์ตามข้อ 3 + ตรวจ version + บันทึก logกลาง
DB-3ย้าย lockStore + classStore (ตอบคำถามเรื่องการตั้งค่าคณะโดยตรง)กลาง
DB-4ย้าย historyStore (ร่างของเจ้าของ / ยืนยันแล้วเห็นทั้งคณะ / กองแผนปลดล็อก)กลาง
DB-5ย้าย ruleStore + rateStore + admissionPlan + sandboxกลาง
DB-6ทดสอบด้วย 2 บัญชีบทบาทเดียวกันคนละเบราว์เซอร์ + บัญชีต่างคณะ (ต้องไม่เห็นกัน) · ตรวจความปลอดภัยของ API ก่อน deployเล็ก

DB-0 ถึง DB-3 ทำให้ผู้ใช้คณะเดียวกันเห็นการตั้งค่าเดียวกันได้ ส่วนงานที่เหลือทยอยทำได้ทีละ store
