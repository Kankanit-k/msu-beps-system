# ข้อเสนอการออกแบบ Cost Allocation, Mapping และ ER

## 1. ขอบเขตและข้อจำกัดของการตรวจสอบ

เอกสารนี้ออกแบบจากข้อมูลในเอกสารโครงการที่มีอยู่ในพื้นที่โครงการ ได้แก่ แนวคิดของ Master หลักสูตร, Master แยกหมวด, Master โครงสร้าง และประเด็นเรื่องผังบัญชี ERP 4 ระดับ การปันส่วน และมิติเวลา ขณะนี้ยังไม่พบไฟล์ ER Diagram หรือ DDL จริงในพื้นที่โครงการ ดังนั้นส่วนการตรวจสอบ ER ในเอกสารนี้เป็นการตรวจสอบ **แบบเทียบกับข้อกำหนดและเสนอ Target ER** ไม่ใช่การยืนยันว่าโครงสร้างปัจจุบันมีตารางหรือคอลัมน์ตรงตามข้อเสนอแล้ว หากมี ER Diagram, DDL หรือ schema จริง ควรนำมาเทียบแบบ column-by-column ต่อไป

> หลักการสำคัญ: ระบบต้องแยกให้ชัดระหว่างข้อมูลต้นทาง, กติกาการจำแนก, ผลการปันส่วน และผลการคำนวณจุดคุ้มทุน เพื่อให้ตรวจสอบย้อนกลับและเปลี่ยนกติกาได้โดยไม่ทำลายข้อมูลเดิม

## 2. เป้าหมายทางธุรกิจและนิยามข้อมูล

ระบบต้องตอบได้ว่าหลักสูตรใดมีจำนวนนิสิตและรายได้เท่าใด มีต้นทุนคงที่และต้นทุนผันแปรเท่าใด จุดคุ้มทุนอยู่ที่จำนวนผู้เรียนหรือรายได้ระดับใด และผลลัพธ์ส่วนใดมาจากข้อมูลจริงกับส่วนใดมาจากการปันส่วน

| สัญลักษณ์        | ความหมายที่เสนอ                                                             | หมายเหตุควบคุม                                                 |
| ---------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Q                | จำนวนหน่วยกิจกรรมหรือจำนวนนิสิตที่ใช้เป็นฐาน                                | ต้องกำหนด snapshot date และสถานะนิสิต                          |
| TR               | รายได้รวมของหลักสูตร/ช่วงเวลา                                               | ควรแยก billed, collected และ recognized หากมีข้อมูล            |
| TFC              | ต้นทุนคงที่                                                                 | ไม่เปลี่ยนตาม Q ภายในช่วงวิเคราะห์                             |
| TVC              | ต้นทุนผันแปรรวม                                                             | ต้องเก็บ variable cost per unit เพื่อคำนวณ contribution margin |
| TC               | ต้นทุนรวม = TFC + TVC                                                       | ต้อง reconcile กลับยอด ERP                                     |
| BEP units        | จุดคุ้มทุนเชิงจำนวน = TFC / (ราคาหรือรายได้ต่อหน่วย - ต้นทุนผันแปรต่อหน่วย) | ใช้ได้เมื่อหน่วยของรายได้และ Q สอดคล้องกัน                     |
| Allocation basis | ฐานปันส่วน เช่น จำนวนผู้เรียน, FTE, พื้นที่, ชั่วโมงใช้บริการ               | ต้องมี denominator และ effective period                        |

## 3. สถาปัตยกรรมการไหลของข้อมูล

ควรแบ่งระบบเป็น 5 ชั้น ดังนี้

| ชั้น           | หน้าที่                                     | ข้อมูลตัวอย่าง                                                 |
| -------------- | ------------------------------------------- | -------------------------------------------------------------- |
| Landing/Raw    | เก็บข้อมูลต้นทางแบบไม่แก้ความหมาย           | ERP export, API ทะเบียน, ค่าเทอม, ค่าเสื่อม                    |
| Standardized   | ทำความสะอาดรูปแบบและกำหนดชนิดข้อมูล         | trim ข้อความ, รหัสหน่วยงาน, ปีงบประมาณมาตรฐาน                  |
| Master/Mapping | เก็บ crosswalk และกติกาที่อนุมัติ           | account map, organization map, program map, student status map |
| Allocation     | คำนวณและบันทึกผลการปันส่วนแบบมีรุ่นประมวลผล | allocation run, allocation driver, allocation result           |
| Analytics      | สร้างผลจุดคุ้มทุนและรายงาน                  | course cost, contribution margin, BEP scenario                 |

ไม่ควรเขียนผลปันส่วนทับข้อมูล ERP ต้นฉบับ และไม่ควรเก็บเฉพาะยอดสุดท้ายโดยไม่มีรายละเอียดว่าใช้ driver ใด denominator เท่าใด และเป็นกติกาเวอร์ชันใด

## 4. แนวทาง Mapping ระหว่าง ERP กับทะเบียน

### 4.1 Mapping หน่วยงาน

ให้สร้าง `ORG_UNIT_MAP` แยกจากข้อมูลหลักสูตร เพราะฝั่ง ERP อาจมีหน่วยที่ไม่มีนิสิต เช่น สถาบันวิจัย หรือหน่วยสนับสนุน ขณะที่ฝั่งทะเบียนมีคณะ ภาควิชา และหลักสูตร

| ฝั่งทะเบียน   | ฝั่ง ERP         | ความสัมพันธ์ | วิธีจัดการ                                          |
| ------------- | ---------------- | ------------ | --------------------------------------------------- |
| คณะ           | หน่วยเบิกจ่าย    | 1:1 หรือ 1:N | ใช้ direct mapping เมื่อรหัสตรงกัน                  |
| ภาควิชา       | ศูนย์ต้นทุนย่อย  | 0:1 หรือ 1:N | เก็บ mapping ตามช่วงเวลา                            |
| หลักสูตร      | ไม่มีหน่วยตรงกัน | N/A          | ปันส่วนจากระดับคณะ/หน่วยเบิกจ่าย                    |
| หน่วยสนับสนุน | ไม่มีนิสิตโดยตรง | 1:N          | จัดเป็น service pool แล้วกระจายด้วย driver ที่กำหนด |

ทุก mapping ต้องมี `effective_from`, `effective_to`, `mapping_status`, `source_reference` และผู้อนุมัติ เพื่อรองรับการปรับโครงสร้างองค์กร

### 4.2 Mapping หลักสูตร

ห้ามใช้ชื่อภาษาไทยที่ต่อข้อความเป็น business key หลัก ควรใช้ `program_id` หรือรหัสหลักสูตรจากทะเบียนเป็นตัวตนถาวร และเก็บชื่อเป็น attribute ที่เปลี่ยนแปลงได้

คีย์สำหรับการวิเคราะห์ควรประกอบด้วย `program_id`, `academic_year`, `program_version` และอาจมี `faculty_id`, `degree_level`, `student_type` เพื่อป้องกันการรวมหลักสูตรต่างรุ่นเข้าด้วยกันโดยไม่ตั้งใจ

### 4.3 Mapping ผังบัญชีและประเภทต้นทุน

ควรแทนที่การมี `COST_ITEM.budget_code` เป็นรหัสเดี่ยวด้วยตาราง `BUDGET_CATEGORY_MAP` ที่มีคีย์ผสมตามบริบท ERP อย่างน้อยดังนี้:

`program_code + budget_category_code + expense_category_code + sub_expense_code`

คอลัมน์สำคัญควรมี `cost_classification` เป็น `FIXED`, `VARIABLE`, `MIXED`, `UNCLASSIFIED`, รวมทั้ง `fixed_ratio`, `variable_ratio`, `allocation_method_id`, `direct_indirect_flag`, `effective_period` และ `approval_status`

กรณีรายการ 80001 หรือ 90001 ที่มีสัดส่วน 50/50 ต้องเก็บเป็นหนึ่ง mapping ที่มีสัดส่วน ไม่ควรแตกเป็นข้อมูลซ้ำแบบไม่มีความสัมพันธ์ เพราะจะตรวจสอบยอดรวมและปรับสัดส่วนภายหลังได้ยาก

### 4.4 Mapping ประเภทนิสิตและรายได้

ควรมี mapping ระหว่างประเภทนิสิตในทะเบียนกับประเภทอัตราค่าธรรมเนียม โดยแยก `student_type`, `nationality_group`, `study_mode`, `fee_schedule_id` และช่วงเวลาที่มีผล เพื่อป้องกันการใช้ค่าเฉลี่ยเดียวกับนิสิตที่มีอัตราค่าธรรมเนียมต่างกัน

### 4.5 Mapping เวลา

ควรสร้าง `TIME_PERIOD` กลางที่ระบุทั้งปีการศึกษา ภาคเรียน ปีงบประมาณ วันที่เริ่มต้นและสิ้นสุด รวมถึงกติกาการจับคู่ระหว่างปีการศึกษากับปีงบประมาณ ไม่ควรอนุมานจากชื่อชีต เช่น งบประมาณ68 หรือ ค่าธรรมเนียม68 โดยตรง

ตัวอย่างกติกาที่ต้องบันทึกเป็น configuration คือ snapshot ของ Q ณ วันใด, นับนิสิตสถานะใด, รายได้รับรู้ตามภาคเรียนหรือปีงบประมาณ และค่าเสื่อมราคาของปีใด

## 5. กรอบ Cost Allocation ที่เสนอ

### 5.1 ลำดับการปันส่วน

1. จำแนกรายการที่ผูกกับหลักสูตรหรือหน่วยงานได้โดยตรงเป็น direct cost ก่อน
2. รวมรายการที่ผูกกับคณะหรือหน่วยเบิกจ่ายแต่ยังไม่ถึงหลักสูตรเป็น faculty/service pool
3. จำแนกรายการเป็น fixed, variable, mixed หรือ unclassified ตามคีย์ผสมของ ERP
4. แยกรายการ mixed ตามสัดส่วนที่อนุมัติ ก่อนเข้าสู่การปันส่วน
5. ปันส่วน pool ด้วย driver ที่กำหนดและมี denominator ในช่วงเวลาเดียวกัน
6. ตรวจสอบยอดรวมผลปันส่วนกลับไปยังยอดต้นทางทุก batch
7. จัดเก็บ allocation result แบบละเอียดก่อนรวมเป็นรายงานหลักสูตร

### 5.2 ลำดับความน่าเชื่อถือของฐานปันส่วน

ควรใช้วิธีที่สะท้อนการใช้ทรัพยากรจริงมากที่สุดก่อน และใช้จำนวนผู้เรียนเป็นวิธีสำรองเมื่อไม่มีข้อมูลละเอียด

| ระดับ | วิธีปันส่วน       | ใช้เมื่อ                                                        | ความเสี่ยง                          |
| ----- | ----------------- | --------------------------------------------------------------- | ----------------------------------- |
| 1     | Direct tracing    | ERP มี program/project/activity หรือ cost center ที่ผูกหลักสูตร | ข้อมูลอาจไม่ครอบคลุมทุกประเภทต้นทุน |
| 2     | Actual usage      | มีชั่วโมงสอน, ชั่วโมงบริการ, พื้นที่, FTE หรือ transaction จริง | ต้องควบคุมหน่วยและช่วงเวลา          |
| 3     | Student headcount | ไม่มี driver การใช้จริง แต่มี Q ที่เชื่อถือได้                  | อาจไม่สะท้อนการใช้ทรัพยากรต่างกัน   |
| 4     | Program share     | ใช้เมื่อไม่มี Q รายหลักสูตรหรือเป็นค่าใช้จ่ายร่วมทั่วไป         | เป็นวิธีประมาณการ ต้องติดธงคุณภาพ   |

### 5.3 สูตรปันส่วน

สำหรับ cost pool จำนวน `C` และหลักสูตร `p` ที่มี driver value `D_p`:

`Allocation_p = C × D_p / ΣD_all eligible programs`

โดยต้องกำหนดกลุ่ม eligible ให้ตรงกับขอบเขตการให้บริการ เช่น ค่าใช้จ่ายคณะหนึ่งไม่ควรถูกกระจายไปยังหลักสูตรคนละคณะโดยอัตโนมัติ

หากรายการเป็น mixed cost:

`Fixed pool = C × fixed_ratio`

`Variable pool = C × variable_ratio`

จากนั้นจึงปันส่วนแต่ละ pool ด้วย driver ที่เหมาะสม และบันทึกผลแยกประเภทไว้เสมอ

### 5.4 การปันส่วนแบบหลายขั้น

สำหรับหน่วยสนับสนุนกลาง เช่น สำนักงานเลขานุการ ควรใช้แบบ sequential allocation หรือ reciprocal allocation ตามความเหมาะสม หากหน่วยสนับสนุนให้บริการกันเอง ต้องตัดสินใจก่อนว่าจะยอมรับการปันส่วนหลายรอบหรือใช้วิธีจัดสรรครั้งเดียวเพื่อความง่ายในการอธิบายต่อผู้บริหาร

### 5.5 การควบคุมคุณภาพ

ทุก allocation run ต้องตรวจสอบว่า (1) ยอด allocated รวมเท่ากับ pool หลังหักรายการที่ไม่เข้าเกณฑ์, (2) สัดส่วน fixed + variable รวมเป็น 1, (3) denominator ไม่เป็นศูนย์, (4) driver อยู่ในช่วงเวลาเดียวกัน, (5) ไม่มีหลักสูตรถูกจัดสรรซ้ำจาก mapping ที่ทับช่วงเวลา, และ (6) ผลรวมต้นทุนกลับไปยัง ERP ได้ภายใน tolerance ที่กำหนด

## 6. ข้อเสนอ Target ER และการตรวจสอบข้อจำกัด

### 6.1 กลุ่มตารางหลัก

| กลุ่ม        | ตารางเสนอ                                                                       | หน้าที่                                     |
| ------------ | ------------------------------------------------------------------------------- | ------------------------------------------- |
| Source       | `ERP_COST_TRANSACTION`, `REGISTRATION_SNAPSHOT`, `FEE_TRANSACTION`              | เก็บข้อมูลต้นทางและ source key              |
| Time         | `TIME_PERIOD`                                                                   | เชื่อม academic year, semester, fiscal year |
| Organization | `ORG_UNIT`, `ORG_UNIT_MAP`                                                      | หน่วยงานและ crosswalk                       |
| Program      | `PROGRAM`, `PROGRAM_VERSION`, `PROGRAM_ORG_MAP`                                 | ตัวตนหลักสูตรและประวัติ                     |
| Student      | `STUDENT_TYPE`, `STUDENT_STATUS`, `STUDENT_COUNT_SNAPSHOT`                      | นิยาม Q และการจัดกลุ่ม                      |
| Account      | `ERP_ACCOUNT_HIERARCHY`, `BUDGET_CATEGORY_MAP`                                  | ผังบัญชี 4 ระดับและ TFC/TVC                 |
| Allocation   | `ALLOCATION_METHOD`, `ALLOCATION_DRIVER`, `ALLOCATION_RUN`, `ALLOCATION_RESULT` | กติกา รุ่นประมวลผล และผลจัดสรร              |
| Analysis     | `PROGRAM_COST_SUMMARY`, `BEP_SCENARIO`, `BEP_RESULT`                            | ผลวิเคราะห์และ scenario                     |
| Governance   | `DATA_SOURCE`, `IMPORT_BATCH`, `MAPPING_APPROVAL`, `DATA_QUALITY_ISSUE`         | lineage, approval และ issue tracking        |

### 6.2 ข้อจำกัดฐานข้อมูลที่ต้องมี

| ประเด็น       | Constraint ที่เสนอ                                                                                       |
| ------------- | -------------------------------------------------------------------------------------------------------- |
| คีย์ต้นทาง    | เก็บ `source_system`, `source_record_id`, `import_batch_id` และ unique composite key ป้องกันการนำเข้าซ้ำ |
| ผังบัญชี      | unique ตามคีย์ผสม 4 ระดับและช่วงเวลาที่มีผล                                                              |
| สัดส่วน mixed | CHECK `fixed_ratio >= 0`, `variable_ratio >= 0`, และผลรวมเท่ากับ 1 เมื่อ classification = MIXED          |
| ช่วงเวลา      | CHECK วันที่เริ่มต้นไม่มากกว่าวันสิ้นสุด และห้าม mapping ที่ active ซ้อนกันใน business key เดียวกัน      |
| จำนวนเงิน     | ใช้ `DECIMAL` ไม่ใช้ floating point และกำหนด currency/scale ชัดเจน                                       |
| จำนวนผู้เรียน | ใช้จำนวนเต็มไม่ติดลบ และระบุ snapshot date กับ status rule                                               |
| ผลปันส่วน     | unique `(allocation_run_id, source_cost_id, target_program_id, cost_type)` ตาม grain ที่กำหนด            |
| ความครบถ้วน   | ไม่อนุญาตให้ cost classification สำคัญเป็น NULL ใน production แต่อนุญาต `UNCLASSIFIED` ใน staging        |
| การลบข้อมูล   | ใช้ soft delete หรือ versioning กับ master และ mapping ไม่ใช้ hard delete ที่ทำลายประวัติ                |
| Audit         | ทุก run ต้องมี created_by, created_at, approved_by, approved_at และ rule_version                         |

### 6.3 จุดที่ต้องแก้จากแนวคิด ER เดิม

ประเด็นสำคัญที่สุดคือไม่ควรให้ `COST_ITEM` มี `budget_code` เพียงตัวเดียวแล้วเลือก `cost_type` ได้ค่าเดียว เพราะไม่รองรับกรณีรหัสเดียวกันมีความหมายต่างกันตามแผนงาน และไม่รองรับ mixed cost 50/50 การออกแบบควรแยก `ERP_ACCOUNT_HIERARCHY` และ `BUDGET_CATEGORY_MAP` ออกจาก transaction พร้อมเก็บ allocation rule เป็น versioned master

นอกจากนี้ไม่ควรผูกต้นทุนกับหลักสูตรโดยตรงในตาราง transaction หากต้นทางมาจากระดับคณะ ควรเก็บ source organizational grain แล้วให้ `ALLOCATION_RESULT` เป็นตารางเชื่อมผลปันส่วน เพื่อไม่ทำให้ผู้ใช้เข้าใจว่าต้นทุนนั้นเป็น direct cost ทั้งหมด

## 7. ความเสี่ยงและข้อสมมติฐานที่ต้องเสนอผู้บริหาร

ความเสี่ยงสูงสุดไม่ใช่การคำนวณสูตร แต่คือการไม่มีข้อมูล ERP ที่ผูกถึงหลักสูตร หากตรวจสอบแล้วไม่มี program/activity/cost-center dimension ที่ละเอียดพอ ผลรายหลักสูตรจะเป็นผลปันส่วน ไม่ใช่ต้นทุนตรงทั้งหมด จึงควรแสดงในรายงานทั้งยอด direct, allocated และ confidence/quality flag

ผู้บริหารควรอนุมัติหลักการ 4 เรื่องก่อนเริ่ม production ได้แก่ นิยาม Q, เลือกยอดต้นทุนระหว่างวงเงินอนุมัติกับเบิกจ่ายจริง, เกณฑ์รายการ mixed cost และเจ้าของข้อมูลที่มีอำนาจอนุมัติ mapping

## 8. แผนดำเนินงานที่เสนอ

| ระยะ                  | ผลส่งมอบ                                               | เกณฑ์ผ่าน                                    |
| --------------------- | ------------------------------------------------------ | -------------------------------------------- |
| 1. Discovery          | data dictionary, source inventory, ผังบัญชีและหน่วยงาน | เจ้าของข้อมูลยืนยัน grain และช่วงเวลา        |
| 2. Mapping foundation | master/crosswalk และกติกา version 1                    | ไม่มี duplicate key และ mapping มีผู้อนุมัติ |
| 3. Pilot              | allocation 1 คณะหรือกลุ่มหลักสูตร                      | reconcile กับ ERP และอธิบายผลได้             |
| 4. Validation         | scenario และ data quality report                       | ผู้ใช้ธุรกิจรับรองผลและข้อสมมติฐาน           |
| 5. Production         | pipeline, audit, dashboard และคู่มือ                   | ประมวลผลซ้ำได้และตรวจสอบย้อนหลังได้          |

## 9. ข้อเสนอสำหรับการประชุมผู้บริหาร

ข้อความหลักควรสื่อว่าโครงการนี้ทำได้ แต่ความแม่นยำของผลรายหลักสูตรขึ้นกับความละเอียดของ ERP และการอนุมัติกติกาปันส่วน ผู้บริหารไม่ควรพิจารณาเพียงตัวเลข BEP สุดท้าย ควรเห็นแหล่งที่มา สัดส่วน direct/allocated และ scenario เมื่อเปลี่ยน driver หรือสมมติฐาน Q
