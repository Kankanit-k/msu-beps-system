# 1 - ข้อเสนอเพื่อขอความเห็นชอบ

วันนี้เรามาพิจารณาข้อเสนอสำคัญในการยกระดับระบบวิเคราะห์จุดคุ้มทุนระดับหลักสูตร เพื่อให้ข้อมูลการเงินของเรามีความโปร่งใสและตรวจสอบย้อนกลับได้ โครงการนี้จะเกิดขึ้นจริงไม่ได้เลยหากเราไม่เห็นชอบกรอบข้อมูลและกติกาปันส่วนต้นทุนร่วมกันเสียก่อน หัวใจสำคัญในวันนี้มีสามเรื่องหลัก คือ การกำหนดหลักการ mapping ที่แม่นยำ กติการ่วมในการปันส่วนต้นทุน และนิยามผลลัพธ์ทางธุรกิจที่ทุกคนยอมรับร่วมกัน ก่อนที่เราจะเดินหน้าสู่ขั้นตอน production เราจึงต้องขออนุมัติโครงสร้างหลักเหล่านี้จากที่ประชุมครับ และเพื่อทำความเข้าใจว่าทำไมเราต้องจัดระเบียบข้อมูลใหม่ทั้งหมด ให้ดูจากความท้าทายที่เรากำลังเผชิญอยู่ในปัจจุบันครับ

# 2 - ปัญหาที่ต้องแก้

ปัญหาใหญ่ที่เราต้องแก้ในวันนี้คือความไม่สอดคล้องกันระหว่างระบบข้อมูลสองแหล่งที่เราใช้งานอยู่ ระบบทะเบียนนิสิตของเรามีความละเอียดสูงมากเพราะเก็บข้อมูลรายบุคคลและรายหลักสูตร ซึ่งเหมาะแก่การใช้เป็นฐานของจำนวนนิสิตและรายได้ แต่ในฝั่งของระบบ ERP ข้อมูลค่าใช้จ่ายส่วนใหญ่มักจะกองอยู่ที่ระดับคณะหรือสำนักงานเลขานุการเท่านั้น ไม่ได้ผูกติดกับรายหลักสูตรโดยตรง ช่องว่างตรงนี้ทำให้เราไม่สามารถดึงตัวเลขค่าใช้จ่ายมาแปะกับหลักสูตรได้ทันที ตัวเลขจุดคุ้มทุนที่ดีจึงต้องแยกแยะให้ชัดเจนว่าส่วนไหนเป็นต้นทุนตรง ส่วนไหนเป็นต้นทุนที่จัดสรร และต้องมีกติกาการจัดสรรที่อธิบายได้ครับ และเมื่อเราเคลียร์เรื่องความต่างของข้อมูลแล้ว เรามาดูนิยามและตัวชี้วัดที่เราจะใช้ร่วมกันครับ

# 3 - นิยามผลลัพธ์ทางธุรกิจ

การจะคุยเรื่องจุดคุ้มทุนให้เข้าใจตรงกัน เราต้องเริ่มจากการใช้นิยามเดียวกันสำหรับทุกหลักสูตรครับ เรากำหนด Q เป็นจำนวนหน่วยกิจกรรมหรือจำนวนนิสิตตาม snapshot ที่ได้รับการอนุมัติ และกำหนดรายได้รวมหรือ TR ให้ชัดเจนในช่วงเวลาเดียวกัน ฝั่งของต้นทุนเราแยกเป็นต้นทุนคงที่หรือ TFC และต้นทุนผันแปรหรือ TVC เพื่อนำมาคำนวณหาจุดคุ้มทุนหรือ BEP สิ่งสำคัญที่สุดคือจุดควบคุมที่เราต้องล็อกให้ตรงกัน ทั้งเรื่องปีการศึกษา ปีงบประมาณ วันที่นับ Q และเกณฑ์การรับรู้รายได้ เพื่อไม่ให้ตัวเลขเกิดความลักลั่นเมื่อนำไปวิเคราะห์ต่อครับ และเมื่อเรามีนิยามที่ชัดเจนแล้ว ขั้นตอนถัดไปคือการสร้างสะพานเชื่อมข้อมูลหรือ mapping ที่น่าเชื่อถือครับ

# 4 - หลักการ Mapping

การทำ mapping ไม่ควรเป็นแค่การเชื่อมชื่อข้อความแบบชั่วคราว แต่ต้องเป็น master data ที่มีช่วงเวลาและผู้อชุมัติชัดเจน เรากำหนดยกเลิกการใช้ชื่อหลักสูตรภาษาไทยเป็นตัวเชื่อม แต่ใช้รหัส program_id แทน พร้อมทั้งเชื่อมโยงโครงสร้างหน่วยงาน ผังบัญชี และประเภทนิสิตเข้ากับตารางค่าธรรมเนียม ทุก mapping ต้องระบุช่วงเวลาที่มีผลบังคับใช้ มีการจัดเก็บเวอร์ชันและสถานะเพื่อให้เราตรวจสอบย้อนกลับได้เสมอว่าใครเป็นผู้อนุมัติกฎนั้นๆ และเพราะผังบัญชีมีความซับซ้อนมากกว่าแค่รหัสเดียว เราจึงต้องลงลึกถึงโครงสร้างภายในของผังบัญชี ERP ครับ

# 5 - จุดสำคัญของผังบัญชี ERP

จุดสำคัญที่เราต้องระวังคือ รหัสบัญชีชุดเดียวกันใน ERP อาจสื่อถึงประเภทต้นทุนที่ต่างกันได้ ขึ้นอยู่กับบริบทที่เราใช้งานอยู่ เราจึงใช้คีย์ผสม 4 ระดับ ตั้งแต่แผนงาน หมวดงบประมาณ หมวดรายจ่าย ไปจนถึงหมวดย่อย เพื่อให้ตีความได้อย่างถูกต้อง ตัวอย่างเช่น รหัสบัญชีเดียวกันอาจเป็นต้นทุนคงที่ในแผนงานหนึ่ง แต่กลายเป็นต้นทุนผันแปรในอีกแผนงานหนึ่ง ดังนั้นเราจึงเสนอให้สร้างตารางผังบัญชีและ map หมวดงบประมาณที่รองรับทั้งต้นทุนคงที่ ต้นทุนผันแปร และรายการผสม พร้อมระบุอัตราส่วนให้ชัดเจนครับ

# 6 - วิธี Cost Allocation

When we distribute costs down to the program level, we follow a strict hierarchy. We trace directly whenever possible, use actual usage next, and fall back to headcount or program shares only when necessary. Building on our account mapping, this ensures every baht of expense follows its true resource consumption. And once costs are pooled, we have to handle expenses that serve multiple purposes before running our calculations.

# 7 - การจัดการ Mixed Cost และการควบคุม

Not all costs are strictly fixed or variable, so mixed costs require careful separation before allocation. We split them into fixed and variable pools using predetermined ratios to keep our break-even analysis accurate. To maintain data integrity, we enforce strict controls: ratios must sum to one, denominators cannot be zero, and every allocation run must reconcile perfectly back to the ERP totals. This governance framework protects our data lineage as we move into structuring our system architecture.

# 8 - Target ER และ Data Architecture

To make our financial models reliable, we separate our data architecture into five distinct layers. We isolate source data, master tables, allocation rules, and analytics so each layer has a clear purpose. This structure gives us full traceability, allowing us to change allocation rules or rerun models without overwriting original source data. But building this architecture requires us to address underlying database constraints and data quality risks.

# 9 - ข้อจำกัดฐานข้อมูลและความเสี่ยง

Building a reliable cost model means enforcing strict database constraints to prevent duplicate imports and overlapping mapping periods. We must also use precise decimal formats and maintain complete version histories for every rule change. Our primary risk is that ERP data often stops at the faculty level, meaning program costs rely heavily on allocation rather than direct tracking. We mitigate this by clearly separating direct costs from allocated costs and attaching quality flags to every report.
